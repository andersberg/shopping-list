🧠 Project Context

You (Anders) are building a structured grocery input parser that converts short,
informal Swedish shopping list strings (e.g. "2 paket ekologisk mjölk") into
validated JSON objects matching a Zod schema used across backend and client. The
goal is high accuracy, deterministic output, and consistent category/unit
mapping using Cloudflare Workers + Cloudflare AI SDK with the
@cf/meta/llama-3.1-8b-instruct-fast model.

The parser runs server-side in a Hono API endpoint (Deno 2), and the result is
validated and normalized against the shared schema.

⸻

🧩 Architecture Summary

Source of Truth •	A single Zod schema defines the expected fields:

{ item: string, category: string, quantity: number, quantity_unit: string |
null, size_value: number, size_unit: string | null, brand: string | null,
organic: boolean, comment: string | null, unit_normalized: string | null,
total_quantity_value: number, total_quantity_unit: string | null,
store_normalized: string | null, store_raw: string | null, offer_quantity:
number, offer_total_price_value: number, offer_currency: string | null,
offer_unit_price_value: number, status: "ok", error: string | null }

Prompt Builder •	A TypeScript function prompt_builder() dynamically constructs
an XML-style system prompt for the model. •	It injects lists (categories,
quantity_units, size_units, brands, stores) from backend constants — ensuring
there is one single source of truth shared across parsing, schema validation,
and prompt generation.

Cloudflare AI Flow 1.	System builds the XML prompt with <system>,
<assistant_context>, and <user_input> sections. 2.	The prompt is passed as a
single string to the model (Cloudflare AI supports both message arrays and
single prompts — we use single for compactness and determinism). 3.	The model
returns pure JSON (no explanations). 4.	The response is parsed, validated, and
logged.

⚙️ Prompt Design Evolution

Initial version •	Simple few-shot text with category/unit hints. •	Model
performed reasonably but with many nulls and misclassifications.

Iteration 1 – Structured XML prompt •	Switched to
<prompt><system><assistant_context><user_input>> format. •	Added explicit
examples and detailed rules. •	Gave the model strong JSON-only instruction.
•	Results improved dramatically (90%+ accuracy).

Iteration 2 – Strict schema & comment fallback •	Introduced a rule: “Never guess
— if unsure, set numeric fields to 0/null and dump unclear words into comment.”
•	Greatly reduced hallucinations; outputs became fully schema-valid.

Iteration 3 – Injected domain lists •	Added runtime injection of categories,
quantity_units, size_units, brands, and stores. •	This unified the model’s
context with backend constants (true single source of truth).

Iteration 4 – Context refinement •	Added examples for edge cases (“ett par
tomater”, “lite grädde”, “Zeta olivolja 500 ml”). •	Introduced rule for decimals
(1,5 → 1.5). •	Rewrote instructions to be minimal, direct, and model-friendly
for an 8B model.

🔍 Debugging & Diagnostics Process

1. Baseline Test Suite

A set of 25 Swedish test strings was run through the API. Example cases include:
•	"2 paket ekologisk mjölk" •	"1 flaska olivolja" •	"6 st ägg" •	"Zeta olivolja
500 ml" •	"Garant kikärtor burk" •	"ett par tomater" •	"ungefär ett kilo lök"

2. Observed issues

After multiple runs, these consistent error patterns emerged:

Category	Symptom	Example Missing category mapping	Common items returned
category: null.	"ägg", "spaghetti", "smör" Comment echo	The model put unit or
product name back into comment.	"flaska", "olivolja" Lost brand link	Brands not
captured even if clearly present.	"Garant kikärtor burk" Store
normalization	“Ica”, “Coop” stored raw but not normalized.	"från Ica"
Quantity/size confusion	“3 dl grädde” parsed as quantity=3, not size_value=3.	“3
dl grädde” Capitalization drift	“Ärtor” vs “ärtor”, “Spaghetti” vs “spagetti”.

3. Prompt-level Fixes

To address this, we refactored the <assistant_context> with: •	Hard category
overrides for frequent items. •	Binding rules for units, brands, and stores.
•	Comment guards — block dumping units/brands/stores into comment.
•	Normalization block for item casing and total quantity computation. •	Added
<post_checks> to repair missing categories for known items.

This brought accuracy to ≈96–98% on the 25-item test set.

🧩 Prompt Structure (Current)

The XML prompt now looks like this (simplified):

<prompt>
  <system>
    You are a strict Swedish line-item extractor.
    Output ONLY valid JSON. Never guess. If unclear → 0/null and comment.
  </system>

<assistant_context>
<categories>...</categories>
<units>...</units>
<brands>...</brands>
<stores>...</stores> <binding_rules>...</binding_rules>
<examples>...</examples> </assistant_context>

<user_input>2 paket ekologisk mjölk</user_input>
</prompt>

🧠 Lessons Learned •	Explicit lexical bindings (category/unit/brand) work better
than long explanations for 8B models. •	XML tags significantly improve
instruction segmentation and reduce JSON leakage. •	Fewer examples (3–5)
outperform longer lists for this model. •	Separation between SYSTEM and CONTEXT
helps keep reasoning compact. •	Post-repair logic in backend can remain minimal
if prompt handles category fallback.
